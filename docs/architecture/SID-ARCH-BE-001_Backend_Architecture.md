## 2. Pola Arsitektur & Alur Data

```
Controller → Form Request → Service → Repository → Eloquent Model → DB
                               │
                               ├─ Policy (otorisasi per resource)
                               ├─ Support (LetterFormSchema, PublicPageCache, ...)
                               └─ Notification (database sinkron + WebPush via queue)
```

- **Controller** hanya urusan HTTP; memanggil `$this->authorize()` bila ada Policy.
- **Form Request** validasi input. `StoreLetterRequest` membangun aturan secara dinamis dari `letter_types.form_fields` milik desa pemohon (`LetterFormSchema`).
- **Service** satu-satunya tempat `DB::transaction()`, aturan bisnis, dan pengiriman notifikasi. Keputusan approval mengunci baris surat (`lockForUpdate`) lalu memeriksa ulang status/step.
- **Repository** membungkus query yang dipakai lintas service (scope daftar surat, resolve pejabat, counter nomor surat).
- **Event/Listener/Job aplikasi minimal.** Satu job (`SendDisasterAlertNotifications`), dua listener (`RecordWebPushDelivery`, `BroadcastNewDatabaseNotification`), dan tiga event broadcast realtime (7.1); selebihnya notifikasi dikirim langsung dari service. `LetterStatusNotification` memakai `afterCommit()` sehingga baru terkirim setelah transaksi commit.
- `Model::preventLazyLoading()` aktif: gagal keras di test, hanya dicatat (warning) di lingkungan lain.

### Penanganan error & bahasa pesan

Locale aplikasi `id` (`APP_LOCALE`, `APP_FALLBACK_LOCALE`; `APP_FAKER_LOCALE=id_ID`), lihat `docs/SETUP.md`. Request `api/*` atau yang mengharapkan JSON selalu dirender sebagai JSON (`bootstrap/app.php`, `withExceptions`).

- **Validasi (422):** pesan dari `lang/id/validation.php`, dengan nama field diterjemahkan lewat `attributes` (mis. `date_of_birth` → "tanggal lahir"), jadi pesan tidak menyebut nama kolom mentah. `message` berisi pesan error pertama, ditambah "(dan :count kesalahan lainnya)" bila ada lebih dari satu (`lang/id.json`); `errors` memuat semua pesan per field. Pesan kustom di `messages()` Form Request tetap dipakai.
- **Exception domain** (`RegionHasActiveCitizensException`, `RegionContainsCitizensException`, `OccupationInUseException`) dirender dengan pesan dan status code miliknya sendiri.
- **Exception bawaan framework** diganti pesan Indonesia oleh `App\Support\ApiExceptionMessages`:

| Status | Pesan |
|---|---|
| 401 | Sesi Anda telah berakhir. Silakan masuk kembali. |
| 403 | Anda tidak memiliki akses untuk aksi ini. |
| 404 | Data tidak ditemukan. |
| 405 | Metode permintaan tidak didukung. |
| 413 | Ukuran data yang dikirim terlalu besar. |
| 419 | Sesi keamanan kedaluwarsa. Muat ulang halaman lalu coba lagi. |
| 429 | Terlalu banyak percobaan. Silakan coba lagi nanti. |
| 500 (dan 5xx lain) | Terjadi kesalahan pada server. Silakan coba lagi beberapa saat. |
| 503 | Layanan sedang tidak tersedia. Silakan coba lagi beberapa saat. |

  Penggantian hanya terjadi bila pesannya kosong atau masih pesan bawaan Inggris ("Unauthenticated.", "This action is unauthorized.", "No query results for model ...", "CSRF token mismatch.", dst.). Pesan kustom dari `abort()` atau Policy (mis. `abort(404, 'Data pejabat tidak ditemukan.')`) tetap dipakai apa adanya. Untuk 5xx: dengan `APP_DEBUG=false` pesan selalu diganti; dengan `APP_DEBUG=true` error tak terduga dirender bawaan Laravel (detail debug) dan pesan kustom 5xx tidak diganti.

### 3.2 Pipeline approval: `approval_flows` → `flow_steps`

- Satu flow default per desa (`ApprovalFlowSeeder`): step 1 `rt`, step 2 `kepala_desa` (final). Flow hanya dapat **dibaca** lewat API; tidak ada endpoint tulis.
- `letters.status` generik (`pending | in_progress | approved | rejected`); posisi dibaca dari `current_step_order` di-JOIN ke `flow_steps`.
- `letters.flow_id` adalah snapshot saat submit.
- `current_step_order = 0` berarti surat masih menunggu tanda tangan dan belum masuk approver mana pun.
- RW dan Kadus **bukan approver**; menerima FYI setelah RT approve. Kasi/Kaur bukan approver; menerima notifikasi setelah final approve.
- Resolve approver: RT berbasis wilayah (`letters.rt_id`), Kades/Sekdes berbasis posisi dalam desa. `letters.rt_id`/`rw_id`/`hamlet_id` diisi otomatis dari wilayah pemohon saat surat dibuat (`Letter::booted`), sehingga daftar dan akses RT/RW/Kadus tetap di wilayah lama walau pemohon pindah.
- **Tahap dilewati / ditahan** (`LetterFlowService::resolveFromOrder`):
  - non-final dengan pejabat aktif tetapi semuanya pemohon → dilewati (log `RtStageSkippedForOfficialApplicant`); surat langsung berstatus `in_progress` di tahap Kades/Sekdes, sama seperti sesudah disetujui RT;
  - non-final tanpa pejabat aktif (RT kosong) → surat **ditahan** di step itu, log `HeldForVacantApprover`, Staf SIDUTama dinotifikasi (`approver_vacant`); saat RT ditetapkan (promote), RT baru dinotifikasi tentang surat yang menunggu;
  - final tanpa approver eligible selain pemohon (mis. Kades mengajukan saat Sekdes kosong) → tidak pernah dilewati: surat **ditahan** di tahap final (`LetterFlowService::holdForVacantStep`, log `HeldForVacantFinalApprover`, Staf dinotifikasi `approver_vacant`), baik saat diajukan maupun saat RT menyetujui; Kades/Sekdes yang kemudian ditetapkan langsung dapat memutusnya.
- **Per role pemohon:** warga, RW, Kadus, Kasi, Kaur, Staf → RT setempat lalu Kades/Sekdes; RT → tahap RT dilewati bila ia satu-satunya RT aktif (RT aktif lain di RT yang sama memutuskan bila ada); Kades/Sekdes → semua tahap non-final (RT) dilewati (`LetterFlowService::isVillageHeadApplicant`, log `RtStageSkippedForVillageHeadApplicant`), lalu saling menyetujui di tahap final: surat Kades hanya oleh Sekdes, surat Sekdes hanya oleh Kades; pasangan kosong → ditahan (`HeldForVacantFinalApprover`).
- **Setelah terbit (Terapkan & verifikasi hasil):** hanya Kasi/Kaur sesuai `assigned_role` (NULL = keduanya); Staf SIDUTama bukan cadangan (mengubah data lewat Data Penduduk). Surat milik sendiri boleh diterapkan/diverifikasi sendiri, termasuk koreksi nilai (hak jabatan); status log diberi akhiran "oleh pemohon sendiri" (`Letter::isApplicant`). Notifikasi `letter_needs_fulfillment`/`letter_ready_for_print`/`letter_result_submitted` dikirim lewat `OfficialService::notifyLetterHandlers`; bila jabatan yang ditugaskan kosong, Staf menerima `handler_vacant` untuk mengisinya. `LetterResource` mengirim `can_fulfill` dan `can_review_result`.

### 3.3 First-Action-Wins Kades/Sekdes

Keputusan dijalankan di dalam transaksi: `SELECT ... FOR UPDATE` pada surat, cek ulang status aktif dan step `kepala_desa`; request kedua mendapat 409. `approval_level` mencatat `kepala_desa` atau `sekretaris_desa` sesuai jabatan aktor.

### 3.4 Final approve: nomor surat & snapshot

1. `LetterNumberGenerator`: `{classification_code}/{NNN}/Des/{bulan Romawi}/{tahun}` (mis. `470/001/Des/X/2026`). Counter `letter_number_counters` per desa + kode klasifikasi + tahun (unique `uq_letter_counters_classification`); baris lama per jenis surat tetap sebagai riwayat.
2. `expires_at` = waktu persetujuan + `validity_days`, dibulatkan ke akhir hari (23:59:59 zona waktu aplikasi, WIB); `processed_at`.
3. `LetterSnapshotService::captureOnFinalApproval()` membekukan konteks render ke `letters.snapshot` dan `signed_by_official_id` (Kepala Desa aktif saat itu, juga bila Sekdes yang menyetujui). Bila belum ada Kades aktif, snapshot ditunda sampai unduhan pertama. Untuk formulir Layanan Kependudukan, snapshot juga membekukan `service_officials`: nama dan NIK Kepala Desa serta Ketua RT/RW wilayah tiap isian `village_area` (placeholder `{{ pejabat_kepala_desa_nama }}`, `{{ pejabat_rt_<area>_nama }}`, `{{ pejabat_rt_<area>_nik }}`, juga `rw`). Tidak ada gambar TTD: ruang tanda tangan dibiarkan kosong untuk TTD basah. Command `letters:backfill-snapshots` (dijalankan migration `2026_10_11_090300`) membekukan surat approved lama.
4. Pencatatan data hasil layanan di transaksi yang sama: `citizen_businesses` (A01) dan `migrant_workers` (F11, layanan tanpa surat).
5. Notifikasi: pemohon `letter_approved_final`; Kasi/Kaur sesuai `assigned_role` mendapat `letter_needs_fulfillment` (bila ada `data_action`) atau `letter_ready_for_print`.

### 3.5 Saksi & persetujuan pada surat

Tidak ada TTD digital (TTD akun, TTD jabatan, stempel digital, dan reset TTD sudah dihapus). Surat terbit tanpa tanda tangan, dicetak lalu ditandatangani dan distempel basah di kantor desa. Yang tersisa hanya persetujuan saksi:

- **Saksi** (isian NIK ber-`witness` di `form_fields`, `letter_signatures.signer_type = witness`, satu baris per percobaan, baris terbaru = keadaan slot): warga desa ber-akun diminta persetujuannya per surat (`consent`, `pending` -> `signed`; menerima dengan kata sandi); warga desa tanpa akun `rt_check` (nama & No. KK dari data penduduk, diverifikasi RT); NIK di luar data penduduk `manual`. Persetujuan pasangan/kepala KK tujuan F09 memakai mekanisme yang sama.
- Pemilik NIK menyetujui (dengan konfirmasi password) atau menolak; boleh sekaligus memblokir pemohon (`signature_blocks`).
- Anti-penyalahgunaan: jawaban seragam walau NIK tidak punya akun; pembatasan `max_rejections`=3 penolakan dalam `rejection_window_hours`=24 per pasangan pemohon–NIK; permintaan kedaluwarsa `request_ttl_days`=3 (`config/letters.php`). Saksi yang menolak/kedaluwarsa diganti pemohon lewat `POST /letters/{id}/signatures/{nik_isian}` (JSON `nik`, opsional `name`/`family_number`).
- Selama ada saksi yang menunggu, `current_step_order = 0` (log "Menunggu persetujuan saksi"). Begitu semua saksi terisi, `LetterService::beginApprovalIfSigned()` memindahkan surat ke step approval pertama.

### 3.6 Terapkan perubahan data (fulfillment)

`LetterFulfillmentService` (otorisasi `LetterPolicy::fulfill`: surat approved, `data_action` ≠ `none`, Kasi/Kaur sesuai `assigned_role`):
- `GET` menyajikan nilai sekarang vs usulan per kolom `data_fields`;
- `POST` (lock surat, sekali saja) menerapkan nilai akhir (koreksi Kasi/Kaur atau usulan warga) dengan aturan validasi yang sama seperti form data warga Staf SIDUTama. `update_citizen` dapat menonaktifkan warga sekaligus akun login-nya; `create_citizen` mewarisi RT/dusun/KK/alamat pemohon. Hasil disimpan di `letters.fulfillment`, plus status log, activity log `citizen` (`letter_fulfilled`), dan notifikasi ke pemohon.
- Hanya kolom yang didefinisikan jenis surat yang boleh disentuh; tidak ada jalur edit bebas data warga dari surat.

### 3.7 Lampiran

`letter_attachments` (kind `field` | `result` | `attachment`) di disk `private_uploads` folder `letter-attachments/{village_id}/{letter_id}/`. Dibuka lewat `GET /letters/{letter}/attachments/{attachment}` (LetterPolicy::view). Folder dihapus saat surat dihapus atau pengajuan gagal.

### 3.8 Isolasi per desa

`letter_types`, `approval_flows`, `approval_settings`, `occupations`, `official_position_types`, `news_categories`, dll. ber-`village_id`. Service mengambil desa dari akun login; ID milik desa lain diperlakukan 404. API publik memilih desa lewat `village_code` (opsional bila hanya satu desa).

## 4. RBAC & Otorisasi

### 4.1 Peran

`users.role` 9 nilai: `warga, rt, rw, kadus, kasi_pemerintahan, kaur_tu_umum, staf_sid, kepala_desa, sekretaris_desa`. Tier navigasi di SYS/FE hanyalah label. Superadmin belum ada.

### 4.2 Jabatan

- **Jabatan berakun** (enum `OfficialPosition`): kepala_desa, sekretaris_desa, rt, rw, kadus, kasi_pemerintahan, kaur_tu_umum, staf_sid — menentukan `users.role`.
- **Jabatan tanpa akun**: jenis dikelola Staf SIDUTama di `official_position_types` (kode dibuat dari label, tidak dapat diubah; seeder: Kasi Kesejahteraan, Kasi Pelayanan, Kaur Perencanaan, Kaur Keuangan, Staf SIPADES, Staf SISKEUDES). `officials.position` kini VARCHAR(50) berisi nilai enum atau `code` jenis jabatan (`ValidOfficialPosition`).
- Penetapan via `OfficialAssignmentService` (promote/demote/rotate, transaksional, activity log `official`). Foto pejabat wajib saat penetapan/rotasi (disk public). Calon dicari lewat NIK (`POST /officials/candidates/lookup`).

### 4.3 Lapisan otorisasi

1. Middleware grup: `auth:sanctum`, `account.active`, `password.changed`, lalu `role:` per grup endpoint.
2. Policy/Service untuk konteks resource (wilayah RT, desa, step aktif, assigned_role, pemohon).
3. Re-validasi di dalam transaksi untuk aksi keputusan.

Scope ringkas: Staf SIDUTama = operator penuh di desanya (CMS, kependudukan, jabatan, konfigurasi); Kades/Sekdes = approver final tanpa akses CMS; Kasi/Kaur = baca daftar warga, akses surat selesai, Terapkan; RT = approver wilayah; RW/Kadus = baca FYI. Data Penduduk (warga & KK) khusus-baca juga untuk Kades/Sekdes (seluruh desa) dan RT/RW/Kadus (wilayahnya).

### 4.4 API integrasi pihak ketiga

Aplikasi pihak ketiga (Cimart) memanggil `/api/integrations/v1` dari server-nya dengan bearer token milik model `IntegrationClient`, bukan milik user. Isolasinya dua arah:

1. **Token client ditolak di route internal.** `config/auth.php` menetapkan `guards.sanctum.provider = users`, sehingga `Laravel\Sanctum\Guard::hasValidProvider` menolak token yang pemiliknya bukan `User`. Ini penting karena `IntegrationClient` punya kolom `is_active` dan tidak punya `must_change_password`, jadi `account.active` dan `password.changed` tidak akan menolaknya.
2. **Route integrasi hanya menerima token client.** Grup `integrations/v1` memakai `auth:integration` (provider `integration_clients`), lalu `integration.client`. Middleware kedua wajib ada, karena guard Sanctum memeriksa session `web` lebih dulu dan meloloskan User SID yang sedang login dengan `TransientToken` (dianggap punya semua ability). Client nonaktif ditolak `403 integration_disabled`.
3. **Hak per endpoint** lewat Sanctum abilities (`IntegrationAbility`) dan middleware `abilities:`; tanpa ability → `403 ability_forbidden`.
4. **Rate limit** `throttle:integration`: 60 request per menit per client, `429 too_many_attempts` dengan `Retry-After`.
5. **Audit**: activity log `log_name = integration`, causer client (request API) atau Staf SIDUTama (menu Integrasi). NIK dan nilai token tidak pernah dicatat.

Client dibuat dan diubah ability-nya hanya lewat artisan `integration:*`; Staf SIDUTama mengaktifkan/menonaktifkan, menerbitkan token baru (rotate, token lama tetap berlaku), dan mencabut token dari menu Integrasi (`/api/integration-clients`, konfirmasi kata sandi). Logika keduanya di `IntegrationClientService`. Kontrak untuk Cimart: `docs/thirdparty/cimart/api-spec/openapi.yaml`.

**Peringatan bencana SIGAP** (`PUT /alerts/{external_id}`, `POST /alerts/{external_id}/end`, ability `alerts:write`) disimpan di `disaster_alerts` oleh `DisasterAlertService`. Penerimaan memakai `lockForUpdate` per peringatan: pembaruan dengan `sent_at` yang tidak lebih baru diabaikan, peringatan yang diakhiri bersifat final, dan peringatan yang diturunkan staf tetap tersembunyi. Notifikasi ke semua akun aktif desa dikirim lewat job antrean (bukan di request SIGAP) hanya saat peringatan baru tampil atau levelnya naik (`notified_level_rank`). Kontrak: `docs/thirdparty/sigap/api-spec/openapi.yaml`. Halaman publik membaca `GET /public/disaster-alerts` tanpa `PublicPageCache` (peringatan kedaluwarsa karena waktu, dan turunan staf harus langsung terlihat). Staf SIDUTama menurunkan dan menampilkan lagi lewat `/disaster-alerts/{id}/dismiss|restore` (kunci baris yang sama, activity log `disaster_alert`).

### 4.5 Permintaan akun warga (aktivasi, ganti foto, lupa sandi tanpa email)

- **Jenjang pemegang** (`AreaApprovalRouter`): RT wilayah warga, lalu RW, Kepala Dusun, atau Staf SIDUTama bila jenjang di bawahnya kosong. Ditentukan SAAT INI (permintaan yang menunggu ikut berpindah bila susunan pejabat berubah); yang sudah diputuskan tercatat di `decided_level`. Keputusan mengunci baris lalu memeriksa ulang (409 bila sudah diputuskan, 403 bila bukan pemegang). Pemegang menerima notifikasi (`account_registration_submitted`, `profile_photo_requested`).
- **Aktivasi akun** (`AccountActivationService`, tabel `account_registrations`): `POST /register` (NIK + kata sandi + foto wajah dari kamera, persegi 1:1, maks 5 MB; tanpa tanggal lahir) membuat akun **nonaktif** + satu pendaftaran menunggu (unique index parsial per warga). Login akun yang belum aktif dijawab pesan sesuai status pendaftarannya (`loginBlockMessage`). Disetujui: akun aktif dan foto pendaftaran menjadi foto profil. Ditolak: wajib catatan. NIK yang ditolak 3 kali (`MAX_REJECTIONS`) tidak bisa mendaftar online lagi; Staf SIDUTama mengaktifkannya manual (`POST /account-registrations/{id}/manual-activation`) setelah warga diperiksa di kantor desa, dengan kata sandi sementara yang tampil sekali.
- **Ganti foto profil** (`ProfilePhotoRequestService`, tabel `profile_photo_requests`): hanya akun warga, foto dari kamera, satu permintaan menunggu per akun; foto terpasang setelah disetujui pemegang. Staf SIDUTama tetap bisa mengganti foto warga langsung (`UserPhotoService`). Akun pejabat memakai foto pejabat.
- **Lupa kata sandi tanpa email** (`PasswordResetRequestService`, tabel `password_reset_requests`): pengaju yang belum login mengirim NIK + tanggal lahir ke `POST /password-reset-requests` (rute web); semua kegagalan dijawab dengan pesan yang sama agar tidak bisa dipakai menebak data penduduk. Server hanya menyimpan hash token klaim; token aslinya ada di browser pengaju. Staf SIDUTama desa yang sama menyetujui/menolak (`/api/password-reset-requests`); setelah disetujui, pemegang token membuat kata sandi baru paling lambat 24 jam (`approved_until`). Akun Staf SIDUTama tidak bisa memakai jalur ini (pemulihan lewat CLI). Akun ber-email tetap memakai `POST /forgot-password` bawaan Laravel.
- Foto pendaftaran dan permintaan ganti foto ada di disk `private_uploads` (`account-registrations/`, `profile-photo-requests/`) selama diproses atau setelah ditolak, dibuka lewat endpoint `.../photo` oleh petugas yang boleh melihatnya.

## 6. PDF & Dokumen

- Tidak ada file PDF tersimpan; dirender dompdf saat diminta.

Alur: surat terbit → petugas desa mencetak, menandatangani, dan menstempel basah → pemohon mengambil di kantor desa; unduhan pemohon adalah salinan tanpa TTD.
- Placeholder: data pemohon (termasuk `applicant_religion`, `applicant_citizenship` = "Indonesia", dan wilayah pemohon saat pengajuan `applicant_rt`/`applicant_rw` 3 digit, `applicant_dusun`, `pejabat_rt_pemohon_nama`/`pejabat_rw_pemohon_nama` = Ketua RT/RW aktif wilayah itu, dibekukan di `snapshot.applicant.area`; snapshot lama tanpa data ini dicetak bertitik), kop desa (`village_*`, dari profil desa), nomor & tanggal surat, isian form (diformat `LetterValueFormatter`: tanggal, rupiah + terbilang, pilihan), nama/NIK pejabat formulir (`pejabat_*`). Nilai teks di-escape; placeholder tak terpetakan diganti garis.
- Dokumen pendukung (`supporting_template`) dirender dengan cara yang sama.
- Ukuran kertas per dokumen (`PaperSize`): A4 tegak bawaan view; `paper_size = f4` (dokumen utama) atau `paper: f4` (dokumen `documents`/`handwritten_forms`) memanggil `setPaper` 215 x 330 mm; `orientation: landscape` tetap A4 mendatar.
- Pilihan kertas pengunduh (`?paper=a4|f4`) pada `GET /letters/{id}/download`, `/preview`, `/supporting-document`, dan `GET /letter-types/{id}/forms/{key}` (`PaperSize::requested`, nilai lain 422). PDF tetap dirender di kertas bawaan dokumen; bila kertas yang diminta berbeda, `PdfRescaler` (setasign/fpdi + fpdf) menempel tiap halaman utuh ke kertas tujuan dengan skala seragam, di tengah (F4 → A4 ±90%, sisa kiri-kanan; A4 → F4 ±102,4%, sisa atas-bawah). Tata letak dan jumlah halaman tidak berubah, hasil tetap vektor. Nama berkas diberi akhiran ukuran (`surat-{id}-f4.pdf`). Tanpa `paper`, PDF dikirim di kertas bawaan seperti sebelumnya. `LetterResource.documents[].paper` = kertas bawaan tiap dokumen.
- Formulir isi tangan (`handwritten_forms`) dirender sebelum surat ada: hanya placeholder pemohon dan desa yang terisi, sisanya titik-titik. Tidak disimpan; pemohon mengunggah fotonya sebagai lampiran isian `file`.
- Pemohon ditolak mengunduh bila `expires_at` lewat. Status surat tetap `approved`; kedaluwarsa dihitung saat dibaca (`Letter::isExpired()`).

## 7. Notifikasi

- `LetterStatusNotification` → kanal `database` (koneksi `sync`, in-app) dan `WebPushChannel` (diantrekan). Payload memuat `context.letter_id`, `letter_no`, `status`, `applicant`, `is_applicant`; Web Push membawa URL `/buka-notifikasi?...`.
- Langganan Web Push disimpan per perangkat lewat `POST/DELETE /push-subscriptions` (VAPID dari `.env`), dengan `device_label` ringkas dari User-Agent (`DeviceLabel`; User-Agent mentah tidak disimpan). Listener `RecordWebPushDelivery` mengisi `last_success_at`/`last_failed_at` tiap pengiriman. Menu Pelanggan Notifikasi Staf SIDUTama (`GET /web-push-subscribers`) menampilkan akun berlangganan per perangkat dengan status `aktif` (berhasil dikirimi dalam 30 hari), `perlu_dicek`, atau `belum_teruji`, plus ringkasan desa.
- Kode status: `pending`, `approver_vacant`, `approval_reminder`, `rt_approved`, `rt_rejected`, `rt_approved_rw_fyi`, `rt_approved_kadus_fyi`, `kepala_desa_approved`, `kepala_desa_rejected`, `letter_approved_final`, `letter_ready_for_print`, `letter_needs_fulfillment`, `handler_vacant`, `letter_fulfilled`, `letter_expiring_soon`, `letter_expired`, `signature_requested`, `signature_accepted`, `signature_rejected`. Notifikasi akun (in-app + Web Push): `account_registration_submitted`, `profile_photo_requested`, `profile_photo_approved`, `profile_photo_rejected`, `password_reset_requested`; status pendaftaran Cimart lewat `CimartApplicationNotification`.
- Pengingat approval: `ApprovalReminderService` lewat command `approvals:send-reminders` yang dijadwalkan tiap 5 menit di `routes/console.php` (butuh `php artisan schedule:work`; di Docker service `sid_scheduler`). Dikirim sekali per tahap per surat ke approver berwenang (in-app + Web Push) saat `now() >= deadline_at - reminder_hours` (0 = tepat saat deadline); `reminded_at` diisi.
- Pengingat masa berlaku surat: `LetterExpiryReminderService` lewat command `letters:send-expiry-reminders` yang dijadwalkan tiap jam (`withoutOverlapping`). Penerima: pemohon (`letters.submitted_by`, termasuk pejabat yang mengajukan surat pribadi, `is_applicant = true`) yang akunnya aktif. Hari H = sehari setelah tanggal `expires_at`; titik H-n jatuh tempo (H - n hari) pada jam kirim desa (`villages.expiry_reminder_send_at`, nilai awal 09:00, jam bulat 06:00–21:00, diubah lewat `PATCH /letter-expiry-reminder-settings/send-at`). Titik H-30/H-14/H-7/H-3/H-1 dinyalakan atau dimatikan Staf SIDUTama (`letter_expiry_reminder_settings`, `GET/PATCH /letter-expiry-reminder-settings`); hari H selalu dikirim. Pencarian hanya mengambil surat yang hari H-nya belum lewat lebih dari masa tenggang + 1 hari. Surat yang gagal diproses dicatat ke log dan dilewati; command keluar dengan status gagal dan surat itu dicoba lagi di run berikutnya.
  - Titik sah: aktif, sudah jatuh tempo, lebih kecil dari `expiry_notified_days`, jatuh temponya setelah `processed_at` dan setelah `activated_at` titik itu. Satu run mengirim satu notifikasi per surat dari titik sah terdekat ke hari H; titik yang lebih jauh dianggap selesai.
  - `letter_expiring_soon` (ikon `clock`, warna `amber`) sebelum surat terkunci; tidak dikirim antara pukul 00.00 dan jam kirim pada hari H. `letter_expired` (ikon `clock`, warna `red`) di hari H. Pesan menyebut sisa hari sebenarnya; `context` ditambah `reminder_days` (titik) dan `days_left` (sisa hari). Tag Web Push tetap `letter-{id}`.
  - Hari H lewat lebih dari `expired_notice_grace_days` (3): kolom diisi 0 tanpa notifikasi.
  - Klaim memakai row lock (`findForUpdateOrFail`) karena mass update ke `letters` dilarang (`EloquentOnlyWritesTest`); kolom diisi lewat model tanpa menyentuh `updated_at`.
- Pengumuman beranda: command `announcements:prune` dijadwalkan tiap menit di `routes/console.php` dan menghapus pengumuman yang lewat `expires_at` per model (event `deleted` ikut menggugurkan cache publik). Pembacaan memakai scope `active()`, jadi pengumuman basi tidak tampil walau scheduler terlambat.
- Tidak ada notifikasi email status surat.

### 7.1 Realtime (Laravel Reverb)

Pengganti polling frontend untuk notifikasi, surat, dan peringatan bencana. Rencana dan keputusan: `docs/task/feature/realtime-reverb.md`.

- **Isi event hanya sinyal** `{ type, id }`. Frontend meng-invalidate cache lalu mengambil ulang lewat endpoint REST yang sudah ada, jadi aturan akses tetap di satu tempat dan data warga (nama, NIK, isi surat) tidak pernah lewat WebSocket.
- **Pengiriman**: semua event `ShouldBroadcast` (lewat antrean, `sid_worker`) + `ShouldDispatchAfterCommit` + `ShouldRescue`. Reverb yang mati hanya menunda sinyal, tidak menggagalkan aksi pengguna; sinyal tidak mendahului data yang di-commit. `ShouldRescue` menjaga hal yang sama saat broadcast berjalan di dalam request (`QUEUE_CONNECTION=sync`): galatnya hanya dilaporkan ke log. Frontend tetap polling sebagai cadangan.
- **Channel** (`routes/channels.php`, otorisasi `POST /api/broadcasting/auth` dengan middleware `api`, `auth:sanctum`, `account.active`, `password.changed`):

| Channel | Jenis | Boleh | Event |
|---|---|---|---|
| `App.Models.User.{id}` | private | akun itu sendiri (pembanding string, tanpa query) | `notification.created`, `letter.changed` (surat yang diajukannya) |
| `letters.staff` | private | `role !== warga` | `letter.changed` |
| `disaster-alerts` | publik | semua | `disaster-alerts.changed` |

- **`NotificationCreated`**: listener `BroadcastNewDatabaseNotification` pada `NotificationSent` kanal `database` (penerima `User`), tanpa mengubah kelas notifikasi. Notifikasi massal ditandai `App\Notifications\Contracts\BroadcastsInBulk` (`DisasterAlertNotification`) dan dilewati listener; `SendDisasterAlertNotifications` mengirim satu event per kelompok 200 akun (broadcaster memecahnya per 100 channel), bukan satu job per akun.
- **`LetterChanged`**: `LetterRealtimeObserver` (didaftarkan di `AppServiceProvider`) pada `created`, `deleted`, dan `updated` bila ada kolom berubah selain `updated_at`, `expiry_notified_days`, `snapshot`. Bukan hanya `status`: perpindahan giliran (`current_step_order`) mengubah antrean pejabat tanpa mengubah status. Penulisan `letters` selalu lewat Eloquent (`EloquentOnlyWritesTest`), jadi observer menangkap semua jalur. Penerima: `letters.staff` + akun `submitted_by`.
- **`DisasterAlertsChanged`**: dari `DisasterAlertService` saat peringatan diterima, diperbarui, diakhiri SIGAP, diturunkan, atau ditampilkan lagi. Pembaruan yang diabaikan (basi/sudah diakhiri) dan `prune` tidak mengirim sinyal.
- **Konfigurasi browser**: `GET /api/realtime/config` (publik, `RealtimeConfigController`) mengembalikan `{ enabled, key, host, port, scheme }`. `enabled` = `BROADCAST_CONNECTION=reverb` dan `REVERB_APP_KEY` terisi; ini saklar mati realtime. `host/port/scheme` dari `REVERB_CLIENT_*` (`config/sid.php`, kosong = origin halaman). Secret tidak pernah dikirim.
- **Server** (`config/reverb.php`): `REVERB_ALLOWED_ORIGINS` (host halaman, bawaan `*`), client event (whisper) dimatikan (`accept_client_events_from=none`), `REVERB_APP_MAX_CONNECTIONS` (Docker: 900, karena event loop bawaan `stream_select` dibatasi ±1.024 file terbuka).

## 8. Keamanan Data & Audit

- Enkripsi `$casts encrypted`: `citizens.nik`, `families.no_kk`, `families.family_address`, `letters.applicant_nik`, `letters.applicant_address`. Dual-column hash (`nik_hash`, `no_kk_hash`, `applicant_nik_hash`, `letter_signatures.target_nik_hash`).
- Berkas privat (disk `private_uploads`): lampiran surat, hasil dari instansi, foto pendaftaran akun, dan foto permintaan ganti foto. Disk public: logo & foto beranda desa (dioptimasi WebP), foto pejabat, foto anggota organisasi desa (`org-member-photos/`), foto profil akun warga (`user-photos/`), thumbnail berita.
- Login: throttle 5 percobaan per `username|IP`, lockout 1 jam, percobaan gagal dicatat `Log::warning`. Register: 5/menit per IP dan 10/jam per hash NIK.
- `must_change_password` → 403 `password_change_required` kecuali `GET /api/user`, `PUT /api/profile/password`, `/logout`.
- Role tidak cocok dengan grup endpoint → 403 `role_forbidden` (`EnsureUserHasRole`). Role dibaca ulang dari DB setiap request, jadi rotasi/turun jabatan langsung berlaku pada sesi yang masih terbuka.
- Label peran `staf_sid` = "Staf " + `config('sid.app_name')` (`config/sid.php`, env `SID_APP_NAME`) lewat `UserRole::stafSidLabel()`; dipakai juga untuk pesan error.
- Audit: `letter_status_logs` (semua transisi status + alasan sistem) dan activity log untuk `official` (promote/demote/rotate), `citizen` (`letter_fulfilled`, serta `created`/`updated`/`deleted`/`imported` manual), `family` (`created`/`updated`/`deleted`/`socioeconomic_updated`), `user_signature` (`reset`), `user` (`staf_sid_recovered`). Pencatatan data kependudukan manual lewat `PopulationAuditService` (properti `village_id`, `subject_label`, `changes` {field: {old,new}}; NIK/No KK/alamat KK disamarkan). Tindakan atas akun (aktif/nonaktif, ubah akun, reset sandi oleh staf, keputusan permintaan reset sandi, aktivasi pendaftaran, dan ganti foto) dicatat `AccountAuditService` (log `user`, `password_reset_request`, `account_registration`, `profile_photo_request`; kata sandi tidak pernah dicatat). Dibaca Staf SIDUTama lewat `GET /activity-logs/population`, `/letters`, dan `/accounts` (`ActivityLogController`). Activity log sengaja tidak dibersihkan otomatis (`activitylog:clean` tidak dijadwalkan) karena menjadi bukti bila ada sengketa.
- Pemulihan darurat Staf SIDUTama: `php artisan staf-sid:recover --username=...` (`UserService::recoverStafSid`) hanya untuk `staf_sid` aktif; reset kata sandi sementara, `must_change_password`, cabut token & sesi DB.
- `trustProxies('*')` aktif; tidak ada `forceScheme('https')` di aplikasi; cookie session default `SameSite=lax` (`SESSION_SAME_SITE`).

## 9. Performa & Cache

- Index performa (migration `2026_10_11_090600`) untuk kolom FK yang dipakai scope wilayah, urutan, dan eager-load (citizens, letters, letter_approvals, rts, rws, officials, users, families, news).
- Daftar surat & warga berpaginasi di database; ringkasan dashboard (`GET /letters/summary`) dihitung dengan agregasi SQL atas scope yang sama.
- `PublicPageCache`: JSON respons `/public/*` di-cache per desa 10 menit dengan kunci berversi; event `saved/deleted` pada Citizen, News, NewsCategory, VillageRegulation, LetterType, Official, Hamlet, Village, OfficialPositionType, Announcement, VillageInfoPage, VillageOrgPosition, VillageOrgMember menggugurkan cache desa terkait (`AppServiceProvider::boot`). Citizen ikut karena nama pejabat (Sambutan Kepala Desa di `/public/home`, kontak) dan jumlah penduduk publik (`total_population`) dibaca dari data warga.
- `GoogleMapsLinkResolver` (`POST /villages/profile/resolve-map-link`): mengambil titik kantor dari link Google Maps. Redirect diikuti manual maks. 5 hop dengan timeout 5 detik, hanya ke host Google Maps di setiap hop (pencegahan SSRF); body respons tidak dibaca. Urutan pembacaan: pin `!3d..!4d..`, lalu `@lat,lng`, lalu parameter `q`/`query`/`ll`/`center`.
- `VillageImageOptimizer`: logo ≤512 px, foto beranda ≤1920 px, EXIF orientation diterapkan, simpan WebP (fallback PNG/JPEG atau berkas asli).

## 10. Reliabilitas & Operasional

| Constraint | Kondisi source | Catatan |
|---|---|---|
| Queue worker | Web Push diantrekan; notifikasi database sinkron | Stack Docker memakai `QUEUE_CONNECTION=database` dengan service `sid_worker` (`queue:work`); panduan VPS memakai Supervisor worker (`docs/deploy`) |
| Deadline approval | `is_overdue` dihitung saat daftar dimuat; pengingat terjadwal `reminder_hours` sebelum deadline | Satu pengingat per tahap; tidak ada notifikasi overdue terpisah |
| Konkurensi keputusan | Row lock + cek ulang | 409 untuk request kedua |
| Surat tertahan | RT kosong, atau Kades/Sekdes pasangan pemohon kosong → ditahan + notifikasi Petugas | Dilepas saat pejabatnya ditetapkan |
| Realtime | Server Reverb terpisah (`sid_reverb`, `reverb:start` sebagai www-data, healthcheck `GET /up` milik Reverb); event lewat antrean | Opsional: Reverb atau worker mati hanya menunda sinyal, frontend kembali polling. Job broadcast yang gagal masuk `failed_jobs` setelah `--tries=3` |
| Deployment | Docker image `sid-api` (PHP-FPM, juga menjalankan `sid_scheduler`, `sid_worker`, `sid_reverb`) + `sid-web` (Nginx + SPA, meneruskan `/app/` ke Reverb), entrypoint tidak menjalankan migrate/seed | `deploy/docker-compose.yml` |
